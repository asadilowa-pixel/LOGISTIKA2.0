## Контекст и цель

Новый проект (с нуля), первый подпроект более крупной системы: веб-сервис + MAX-бот для логиста,
объединяющий данные МойСклад + Wildberries (WB) + Ozon. Полная система решает 14 требований к
автосинхронизации (см. раздел «Требования» ниже) — не строить систему вокруг ручной выгрузки Excel
в перспективе, но саму систему собрать так, чтобы она работала уже сейчас на выгруженных xlsx-отчётах,
без живых API-ключей WB/Ozon.

Этот подпроект закрывает только «ядро синхронизации»: приём данных, нормализация, хранение,
журнал синхронизаций, статус свежести данных. Дашборд, MAX-бот и живые API-коннекторы
(WB API, МойСклад API, Ozon API) — отдельные последующие подпроекты, вне рамок этой спеки.

## Стек и расположение

- Backend: Python (FastAPI)
- БД: PostgreSQL
- Планировщик: APScheduler (in-process, без Celery/Redis — избыточно для MVP с одним watch-poll)
- Развёртывание: локально на этом ПК, Docker Compose (`backend` + `postgres`, без брокера очередей)
- Путь проекта: `C:\Users\1\Desktop\сервис логиста 2.0`

## Источники данных в MVP

Источник Ozon подключён только как **файловый**: пользователь вручную выгружает xlsx-отчёт
«Управление остатками» из личного кабинета Ozon Seller — как уже делается сейчас (файлы вида
`Управление остатками ....xlsx` в папке калькулятора). Живого API-ключа Ozon нет. Архитектура
рассчитана на то, что `OzonApiSource` добавится позже как вторая реализация того же интерфейса,
без переделки БД/пайплайна.

WB и МойСклад в этом подпроекте присутствуют только как строки-заглушки в таблице `sources`
(тип, включён/выключен) — без коннекторов и без парсинга.

Разделы данных для MVP:
- **Остатки** (`stocks`) — реализуется в этом плане, реальный файл-образец есть
- **FBS заказы + статусы** (`fbs_orders`) — вынесено в отдельный план (нет реального файла-образца
  для проверки маппинга колонок — см. «История ревизий»)

### Маппинг колонок «Остатки» (реальный файл)

Источник: `Управление остатками 24.08.2026 14-43.xlsx`, лист `Товар-склад`.
Строка 1 — заголовки, строки 2–4 — служебные (тип поля / описание), данные — со строки 5.

| Колонка (буква) | Заголовок | Поле в `stocks` |
|---|---|---|
| A | Артикул | `article` (str, обязательное) |
| B | Название товара | `product_name` (str) |
| C | SKU | `sku` (int) |
| D | Признак товара | не используется |
| E | Зона размещения | `placement_zone` (str: `Сортируемый товар` / `Несортируемый товар`) |
| F | Кластер | `cluster` (str) |
| G | Склад | `warehouse` (str, обязательное) |
| H | Доступно к продаже | `quantity_available` (int) |
| I | Недоступно к продаже (Готовим к продаже) | `quantity_preparing` (int) |

Естественный ключ строки: (`article`, `warehouse`) — один артикул может встречаться на нескольких
складах отдельными строками (подтверждено на реальных данных: 738 строк данных в файле-образце).
Строка без `article` или без `warehouse` — невалидна, пропускается, попадает в `error_count`.

## Архитектура источника (Source abstraction)

Единый интерфейс (условно):

```python
class SyncSource(Protocol):
    def fetch_stocks(self) -> list[StockRow]: ...
    def fetch_fbs_orders(self) -> list[FbsOrderRow]: ...
```

MVP-реализация: `FileSource` — парсит xlsx через `openpyxl` (тот же инструмент, что уже
используется в `build_calculator.py` калькулятора отгрузок). `fetch_fbs_orders` в этом плане
не реализуется (см. «Источники данных в MVP»). `OzonApiSource` — заглушка/интерфейс на будущее,
без реализации HTTP-вызовов.

Оба способа приёма файла (watch-папка и HTTP upload) вызывают один и тот же внутренний
`ingest(file_path, section)`, который вызывает `FileSource.fetch_*` и дальше единый пайплайн
нормализации → апсерт в канонические таблицы → запись в журнал.

## Модель данных

| Таблица | Назначение |
|---|---|
| `sources` | Источник: WB / МойСклад / Ozon. Поля: тип (`file` \| `api`), включён ли |
| `source_sections` | Раздел источника (`stocks`, `fbs_orders`, ...), `last_success_at`, интервал опроса (для файлового — интервал watch-poll) |
| `sync_runs` | Журнал: `started_at`, `finished_at`, `source_section_id`, `status` (success/partial/error), `received_count`, `changed_count`, `error_count`, `error_message` |
| `ingested_files` | Хеш файла + время загрузки + `sync_run_id` — дедуп повторной загрузки того же файла |
| `stocks` | Канонические текущие остатки: `article`, `warehouse`, `product_name`, `sku`, `placement_zone`, `cluster`, `quantity_available`, `quantity_preparing`, `source_run_id`. Апсерт по ключу (`article`, `warehouse`) |
| `fbs_orders` *(следующий план)* | Канонические FBS-заказы: `order_id`, статус, `source_run_id`. Апсерт по `order_id` |
| `order_status_history` *(следующий план)* | История смены статусов FBS-заказа (нужна для подсчёта «изменено» в журнале и для будущих уведомлений) |

Канонические таблицы (`stocks`, `fbs_orders`) **никогда не truncate** — только апсерт. При ошибке
разбора файла старые данные в них не трогаются (требование 12).

## Приём и обработка файлов

Два равноправных способа загрузки, ведущих к одному и тому же `ingest()`:

1. **Watch-папка** — APScheduler проверяет заданную папку на диске раз в N секунд. Новый или
   изменившийся (по хешу содержимого) файл — в очередь на ingest.
2. **`POST /sync/{source}/{section}/upload`** — ручная загрузка файла (multipart) через HTTP,
   ingest выполняется сразу. Это же и есть «запустить синхронизацию вручную» (требование 11).

Дедуп (требование 4): хеш файла проверяется в `ingested_files` — повторная загрузка того же файла
не создаёт новый `sync_run` с изменениями (или создаёт run со статусом «файл уже обработан»,
без апсертов).

Определение новых/изменённых записей (требование 5): при апсерте строка сравнивается с текущим
значением в канонической таблице — если отличается, счётчик `changed_count` в `sync_runs`
увеличивается (для FBS-заказов в следующем плане дополнительно будет писаться запись в
`order_status_history`).

## API-поверхность (MVP)

- `POST /sync/{source}/{section}/upload` — ручная загрузка xlsx
- `GET /sync/status` — по каждому источнику/разделу: `last_success_at`, статус последней попытки,
  свежесть данных (требования 6, 14) — эндпоинт, который будущий дашборд будет опрашивать напрямую
- `GET /sync/runs?source=&section=&limit=` — журнал синхронизаций (требование 7)

## Обработка ошибок

- Не распарсился файл целиком (битый xlsx, нет нужного листа) → `sync_run.status = error`,
  `error_message` заполнен, канонические таблицы не трогаются.
- Отдельная строка внутри файла не распознана (нет артикула, некорректное число) → строка
  пропускается, попадает в `error_count`, остальные строки файла обрабатываются нормально
  (партиальный успех — `status = partial`).
- Ретрай (требование 8): для файлового источника не нужен (нет сети) — повторная загрузка файла
  пользователем и есть ретрай. В интерфейсе `SyncSource` предусмотрен retry-хук (позже обёртка
  через `tenacity`) для будущего `WBApiSource` — сейчас не реализуется.
- Уведомление об ошибках (требование 10) — вне рамок; `GET /sync/status` и `GET /sync/runs`
  дают данные, которые в следующем подпроекте (MAX-бот) будут читаться и превращаться в алерты.

## Тестирование

1. Загрузка корректного xlsx с остатками (реальный файл-образец) → строки появляются в `stocks`,
   `sync_runs.status = success`, `received_count`/`changed_count` совпадают с ожидаемым (738 строк).
2. Повторная загрузка того же файла (без изменений) → дедуп по хешу, апсертов нет.
3. Загрузка файла с изменённым количеством по части артикулов → `changed_count` считает только
   изменившиеся строки, `stocks` обновлены только для них.
4. Файл с одной некорректной строкой (нет артикула) → `status = partial`, ошибочная строка в
   `error_count`, остальные строки применены.
5. Битый/нечитаемый xlsx → `status = error`, `stocks` не изменены (проверка требования 12).
6. `GET /sync/status` после серии успех/ошибка/успех показывает `last_success_at` последнего
   **успешного** запуска, а не последней попытки.
7. Watch-папка: файл, добавленный в папку, подхватывается APScheduler без ручного вызова upload.

FBS-специфичный тест-кейс («заказ меняет статус между загрузками» → запись в `order_status_history`)
переносится в следующий план вместе с самим разделом FBS.

## Вне рамок (не реализуем в этом подпроекте)

- Живые вызовы WB API, МойСклад API, Ozon API (`OzonApiSource` и т.п.) — только интерфейс/заглушка.
- Учёт лимитов конкретных методов API — актуально только при живом коннекторе.
- Веб-дашборд («Центр синхронизации» в UI) — отдельный подпроект, потребляет `GET /sync/status`.
- MAX-бот и уведомления об ошибках — отдельный подпроект, потребляет `GET /sync/runs`.
- Раздел «FBS заказы + статусы» — отдельный следующий план (нет реального файла-образца сейчас).
- Синхронизация логистических расходов, поставок, возвратов, финансовых отчётов — вне рамок MVP.
- Аутентификация/авторизация API-эндпоинтов — однопользовательский локальный MVP.
