# Сервис логиста 2.0 — веб-дашборд — дизайн

Дата: 2026-09-09
Статус: согласована с пользователем в чате (см. историю обсуждения), готова к плану реализации

## Контекст и цель

Существующий backend (`app/`) — read-only FastAPI-слой поверх боевого ClickHouse-хранилища
(`151.247.208.105:8123`), которое наполняется внешней системой данными Ozon/WB/МойСклад.
Сейчас у сервиса нет UI — только JSON API (`/stocks/*`, `/mysklad/*`, `/watchdog/*`).

Этот подпроект добавляет **веб-дашборд как главную страницу сервиса** (`GET /`) для команды
(несколько человек в локальной сети, без выхода в интернет). Дашборд показывает три блока:
остатки, расходы на логистику, количество заказов ФБС.

Вне рамок этого подпроекта: свежесть данных (`watchdog.*`) — не включается в эту версию
дашборда по решению пользователя, можно добавить отдельной задачей позже.

## Стек

Без изменений: Python, FastAPI, `clickhouse-connect`. Фронтенд — **не SPA**: один HTML-файл,
отдаваемый FastAPI, плюс vanilla JS, обращающийся к JSON-эндпоинтам того же сервиса через
`fetch`. Никакой сборки/npm/node — по явному выбору пользователя ("просто: шаблоны FastAPI +
HTML/JS").

## Авторизация

**HTTP Basic Auth** поверх всего приложения (и HTML-страницы, и всех JSON-эндпоинтов) —
самый простой вариант для внутреннего инструмента без интернета: браузер сам показывает
системное окно логина/пароля, отдельная страница логина не нужна.

- Логин/пароль — новые переменные окружения `DASHBOARD_USER` / `DASHBOARD_PASSWORD` в
  `app/config.py` (`Settings`) и `.env` (по аналогии с `CLICKHOUSE_*`).
- Реализация — ASGI-мидлварь (`app/auth.py`), а не `Depends()` на каждый роут: `Depends()` не
  покрывает статику, отдаваемую через `StaticFiles`/произвольный `Response`, мидлварь
  единообразно защищает всё приложение одним местом.
- Сверка пароля — `secrets.compare_digest` (защита от timing-атак), не `==`.
- Неавторизованный запрос → `401` с заголовком `WWW-Authenticate: Basic realm="..."` (иначе
  браузер не покажет системное окно логина).
- Один общий логин/пароль на всех — без разделения пользователей (по решению пользователя).

## Новые эндпоинты

### `GET /expenses/logistics`

Параметры: `date_from: date`, `date_to: date` (оба обязательные — без периода запрос
бессмысленный на 865k+ строк), `id_client: int | None`.

Источник — `ozon.expenses_agg` (МойСклад/WB источника нет, см. ниже). Расход на логистику за
период считается как сумма четырёх полей таблицы:

```sql
SELECT
    sum(logistick_cost) AS logistics_cost,
    sum(returned_logistick_cost) AS returned_logistics_cost,
    sum(last_mile_cost) AS last_mile_cost,
    sum(cancel_last_mile_cost) AS cancel_last_mile_cost
FROM ozon.expenses_agg
WHERE date_operation BETWEEN {date_from:Date} AND {date_to:Date}
  [AND id_client = {id_client:UInt8}]
```

Ответ:

```json
{
  "date_from": "2026-08-01",
  "date_to": "2026-08-31",
  "ozon": {
    "logistics_cost": 12345.67,
    "returned_logistics_cost": 234.56,
    "last_mile_cost": 3456.78,
    "cancel_last_mile_cost": 12.34,
    "total": 16049.35
  },
  "wb": null
}
```

`wb: null` — не placeholder-заглушка ошибки, а честный ответ «данных пока нет»:
`wildberies.logistics_costs` существует в схеме ClickHouse, но на момент написания спеки
содержит 0 строк (наполняется той же внешней системой, что и остальные таблицы; WB API-доступ
для логистических расходов туда пока не подключён — вне контроля этого сервиса). Реализация
обязана реально проверить количество строк по параметрам запроса (`count()` с тем же `WHERE`),
не хардкодить `null` — когда внешняя система начнёт писать данные, поле должно само
"ожить" без изменений кода. `total` считается только если у `ozon` есть данные.

### `GET /orders/fbs-count`

Параметры: `date_from: date`, `date_to: date` (обязательные), `id_client: int | None`.

```sql
-- Ozon
SELECT count() FROM ozon.ozon_fbs_postings
WHERE in_process_at BETWEEN {date_from:Date} AND {date_to:Date}
  [AND id_client = {id_client:UInt8}]

-- WB
SELECT count() FROM wildberies.orders
WHERE fbs = 1 AND date BETWEEN {date_from:Date} AND {date_to:Date}
  [AND id_client = {id_client:UInt8}]
```

Ответ:

```json
{"date_from": "2026-08-01", "date_to": "2026-08-31", "ozon": 1234, "wb": 567}
```

Оба маркетплейса реально наполнены (75k и 81k строк соответственно) — `null` здесь не
ожидается, оба поля всегда числа (`0`, если заказов в периоде нет).

### Общее для обоих эндпоинтов

- Параметризованные ClickHouse-запросы (`{name:Type}`), как во всех существующих
  `fetch_*`-функциях — без строковой склейки значений фильтров.
- `date_from`/`date_to` валидируются FastAPI как `datetime.date` из query-строки
  (`YYYY-MM-DD`); `date_from > date_to` → `400`.
- Модели ответа — `pydantic.BaseModel` (не `dataclass`, как для read-моделей строк) — это
  агрегаты/вычисляемые объекты, не отражение строки таблицы 1:1.

## `GET /` — страница дашборда

Отдаётся не через `StaticFiles`, а отдельным роутом (`app/routers/dashboard.py`), который
возвращает `FileResponse`/строку HTML — попадает под общую auth-мидлварь так же, как API.

Один HTML-файл (`app/static/dashboard.html`) + один JS-файл (`app/static/dashboard.js`), без
шаблонизатора (Jinja2 не нужен — вся динамика через `fetch` на существующий и новые JSON API,
статических данных для сервер-сайд рендеринга нет). CSS — инлайн в HTML или отдельный
`app/static/dashboard.css`, на усмотрение реализации (не принципиально для дизайна).

Разметка — три блока сверху вниз:

1. **Общий фильтр периода** — два `<input type="date">` (от/до), применяется к блокам
   «Расходы» и «ФБС-заказы» (не к «Остаткам» — там нет понятия периода, это текущий срез).
   Значение по умолчанию при загрузке страницы — последние 30 дней.
2. **Остатки** — таблица, дергает `GET /stocks/unified`. Фильтры над таблицей:
   `<select>` маркетплейс (все/Ozon/WB), текстовое поле `id_client`. Колонки — все поля
   `UnifiedStock`.
3. **Расходы на логистику** — две карточки (Ozon / WB), дергает `GET /expenses/logistics` с
   текущим периодом. WB-карточка при `wb: null` показывает текст «нет данных».
4. **Заказы ФБС** — две карточки (Ozon / WB) со счётчиком, дергает `GET /orders/fbs-count` с
   текущим периодом.

Изменение периода или фильтров остатков перезапрашивает соответствующий блок (не всю
страницу) — обычный `fetch` + перерисовка DOM, без фреймворка.

## Тестирование

Как и весь существующий код — на `FakeClient`/`FakeQueryResult` (`tests/fake_client.py`), без
обращения к реальному серверу в автоматических тестах; ручная проверка на живых данных перед
коммитом (как делалось для всех предыдущих фич).

- `fetch_logistics_expenses`: маппинг сумм, `WHERE ... BETWEEN`, `id_client`-фильтр,
  `wb: None` когда строк 0.
- `fetch_fbs_order_count`: подсчёт по обоим маркетплейсам, `id_client`-фильтр.
- `date_from > date_to` → `400` на обоих эндпоинтах.
- Auth-мидлварь: без заголовка → `401` + `WWW-Authenticate`; неверный пароль → `401`; верный →
  запрос проходит дальше.
- `GET /` без авторизации → `401` (не `200` с HTML) — подтверждает, что мидлварь покрывает и
  страницу, не только API.

## Открытые вопросы (не блокируют реализацию)

- Расходы на логистику WB: показывать «нет данных», пока `wildberies.logistics_costs` пуста.
  Пользователь отложил обсуждение источника (WB API/доступ) — не в рамках этого подпроекта.
- Индикатор свежести данных (`watchdog.*`) на дашборде — осознанно не входит в эту версию,
  можно добавить отдельной задачей.

## Вне рамок

- Разделение пользователей/ролей — один общий логин/пароль.
- HTTPS/TLS — внутренняя сеть без выхода в интернет.
- Graph/чарты, экспорт в Excel, пагинация таблицы остатков — не запрошено, не делаем (YAGNI).
- МойСклад-блок на дашборде — не запрошен в этой итерации (эндпоинты `/mysklad/*` уже есть в
  API, но на дашборд не выводятся).
