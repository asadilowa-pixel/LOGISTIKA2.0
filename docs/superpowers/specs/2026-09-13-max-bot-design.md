# Сервис логиста 2.0 — бот в MAX (бронь FBO + алерты ФБС) — дизайн

Дата: 2026-09-13
Статус: согласована с пользователем в чате (см. историю обсуждения), готова к плану реализации

## Контекст и цель

Существующий backend (`app/`) — read-only FastAPI-слой поверх ClickHouse-реплики, которую
наполняет внешняя система. Этот подпроект добавляет **бота в мессенджере MAX** для логиста —
отдельный подпроект по отношению к веб-дашборду, работает в том же процессе/репозитории, но
как самостоятельный набор модулей.

Бот решает две задачи:

1. **Бронь поставок FBO** на Ozon и Wildberries — через личные API-ключи продавца
   (не через ClickHouse-реплику, в которой нет операций записи и нет нужной гранулярности
   статусов).
2. **Мониторинг ФБС-заказов**: сколько заказов сейчас нужно отгрузить, сколько времени
   осталось до дедлайна передачи в доставку, алерт при риске просрочки (штраф).

Работает с несколькими кабинетами (аккаунтами продавца) на каждой площадке.

## Важные ограничения, подтверждённые исследованием

- **MAX Bot API** — намеренно копирует структуру Telegram Bot API (эндпоинты, `Update`,
  инлайн-кнопки с callback). Официального Python SDK нет — вызываем HTTP напрямую.
  Транспорт: long polling (`GET /updates`, домен `platform-api2.max.ru`) или webhook
  (нужен публичный HTTPS с реальным сертификатом + доверие корневого сертификата Минцифры).
  **Для v1 выбран long polling** — сервис работает локально, без публичного домена.
- **Ozon Seller API** — есть эндпоинты для драфтов поставки и таймслотов
  (`/v1/draft/create`, `/v2/draft/timeslot/info` и далее), но точные имена полей/методов
  подтверждены только косвенно (официальный `dev.ozon.ru` недоступен для прямого фетча из
  этой среды — редиректы). **Требуется проверка на реальных ключах в сэндбоксе перед
  реализацией** (см. «Открытые вопросы»).
- **Wildberries API** — подтверждено официальной документацией (`dev.wildberries.ru`,
  раздел «FBW Supplies» / `informationForFormingSupplies`): доступны только справочные
  методы — `GET /api/v1/warehouses` (склады), `POST /api/v1/acceptance/options` (проверка
  допустимости склада по штрихкоду/количеству — **не бронирование**), `POST /api/v1/supplies`
  (список существующих поставок со статусами). **Официального метода бронирования
  конкретной даты/слота поставки в документации нет** — судя по всему, назначение даты
  делается только в личном кабинете. По решению пользователя: в v1 для WB реализуются
  только алерты о коэффициентах, бронь остаётся ручной (в ЛК). Проверка «а вдруг есть
  скрытый метод» на реальном кабинете — отдельный спайк, не блокирует основную реализацию.
- ClickHouse-реплика ФБС-заказов (`ozon.ozon_fbs_postings`, `wildberies.orders`) содержит
  только финальные/почти финальные статусы (`delivered`/`cancelled`/`delivering`) — не
  подходит для мониторинга «сейчас к отгрузке». ФБС-мониторинг бота обязан ходить в живые
  API Ozon/WB, а не в ClickHouse.

## Доступ

Один общий рабочий чат/группа в MAX. Бот обрабатывает команды/кнопки только из этого чата
(`chat_id` фиксируется в конфиге), сообщения из других чатов игнорируются.

## Масштаб v1

| Площадка | Бронь FBO | Мониторинг ФБС + алерты |
|---|---|---|
| Ozon | Полная (создание драфта в боте **и** выбор существующего черновика из ЛК, авто-бронь по диапазону дат) | Полная |
| Wildberries | Только алерты о свободных/бесплатных коэффициентах, бронь — руками в ЛК | Полная |

## Компоненты

Новый модуль `app/bot/`, работает в том же процессе FastAPI как фоновая asyncio-задача,
запускаемая в существующем `lifespan` (`app/main.py`) — без отдельного процесса/супервизора.

| Модуль | Роль |
|---|---|
| `max_client.py` | HTTP-клиент к `platform-api2.max.ru`: long polling `/updates`, отправка `/messages`, инлайн-кнопки, `/answers` на callback |
| `ozon_client.py` | Ozon Seller API: драфты, таймслоты, бронь, список FBS-отправлений со статусом/дедлайном |
| `wb_client.py` | WB API: склады, коэффициенты приёмки, список существующих поставок, список ФБС-заказов |
| `state.py` | SQLite-файл `bot_state.db` — рабочее состояние бота (не ClickHouse, который остаётся read-only внешней репликой) |
| `handlers.py` | Разбор входящих команд/кнопок → вызов нужного flow |
| `flows/booking.py` | Обе схемы брони FBO для Ozon + вотчер коэффициентов для WB |
| `flows/fbs_status.py` | Команда «к отгрузке» + фоновый джоб алертов по дедлайну |
| `scheduler.py` | `AsyncIOScheduler` (APScheduler, без Celery/Redis — как и в остальном проекте): джоб опроса слотов/коэффициентов, джоб проверки дедлайнов ФБС |

### Креды и конфигурация кабинетов

Несколько кабинетов на площадку. Конфиг по конвенции именования в `.env`/`Settings`,
привязка к тем же `id_cabinet`, что уже используются в ClickHouse-таблицах (для консистентности
с дашбордом):

```
OZON_CABINET_<id_cabinet>_NAME=...
OZON_CABINET_<id_cabinet>_CLIENT_ID=...
OZON_CABINET_<id_cabinet>_API_KEY=...

WB_CABINET_<id_cabinet>_NAME=...
WB_CABINET_<id_cabinet>_TOKEN=...

MAX_BOT_TOKEN=...
MAX_CHAT_ID=...
```

## Data flow

### Ozon FBO — способ A: создать драфт в боте
1. Команда в чате → бот спрашивает кабинет (если их несколько), артикулы/SKU, склад,
   диапазон дат.
2. `POST /v1/draft/create` → poll `/v1/draft/create/info` → `draft_id`.
3. `/v2/draft/timeslot/info` на диапазон дат.
   - Слот с коэффициентом 0 есть сразу → бронируем, подтверждаем в чат.
   - Только платный слот (коэффициент > 0) → кнопка «забронировать за N ₽» с явным
     подтверждением человеком — **не бронируем платный слот автоматически**.
   - Слотов нет вообще → создаём `watch_request` (`status=watching`), планировщик опрашивает
     `/timeslot/info` периодически (интервал с запасом от документированного лимита
     ~2 запроса/сек на этот метод, общего для всех продавцов).

### Ozon FBO — способ B: существующий черновик из ЛК
1. Бот пытается показать список черновиков через API.
   **Не проверено, видит ли API черновики, созданные руками в ЛК** — первый пункт
   технической проверки перед реализацией (см. «Открытые вопросы»). Если не видит —
   fallback: логист вводит номер/`draft_id` поставки вручную в бота.
2. Далее — тот же watch-and-book цикл, что в способе A (включая правило про платные слоты).

### Wildberries — только алерты по коэффициенту
1. Логист регистрирует наблюдение: склад + желаемый коэффициент (по умолчанию 0) +
   диапазон дат.
2. Планировщик опрашивает `GET /api/tariffs/v1/acceptance/coefficients` (интервал с учётом
   лимита запросов — уточняется на реальном кабинете, ориентир из вторичных источников —
   единицы запросов в минуту).
3. Подходящий коэффициент → алерт в чат (склад, дата, коэффициент). Дедуп: повторный алерт
   по тому же (склад, дата) не чаще настроенного периода (по умолчанию раз в час), пока слот
   держится.

### Мониторинг ФБС (Ozon + WB)
- **По команде**: агрегирует «к отгрузке» + время до ближайшего дедлайна по каждой
  площадке/кабинету — из живых `GET /v3/posting/fbs/unfulfilled/list` (Ozon) и
  `GET /api/v3/orders/new` (WB).
- **По расписанию** (каждые `FBS_POLL_INTERVAL_MINUTES`, по умолчанию 15 минут): та же
  выборка; для каждого заказа, где до дедлайна осталось меньше `ALERT_HOURS_BEFORE_DEADLINE`
  (по умолчанию, значение общее для обеих площадок в v1) и алерт по нему ещё не отправлялся —
  алерт в чат + запись в `alert_log` (дедуп по `order_id`).
- Расчёт риска штрафа в v1 — **пороговая логика по времени до дедлайна**, не точный расчёт
  суммы штрафа (у Ozon и WB сложные и часто меняющиеся формулы штрафов — см. исследование).

## Хранение состояния

`bot_state.db` (SQLite, локальный файл, отдельно от ClickHouse):

- `watch_requests(id, marketplace, cabinet_id, kind, reference_json, date_from, date_to, max_coefficient, status, requested_by_chat_id, created_at, updated_at)`
  — `kind`: `ozon_draft_create` | `ozon_draft_select` | `wb_coefficient`
  — `status`: `watching` | `booked` | `awaiting_confirmation` | `failed` | `expired` | `cancelled`
- `alert_log(id, marketplace, cabinet_id, order_key, alert_type, sent_at)` — уникальность по
  (`marketplace`, `cabinet_id`, `order_key`, `alert_type`), предотвращает повторные алерты за
  один и тот же случай.

## Обработка ошибок

- Сетевые ошибки / 429 от MAX и от маркетплейсов — retry с backoff (`tenacity`); фоновая
  задача не должна падать целиком — ошибка одной итерации логируется, цикл продолжается.
- Платный слот найден → не бронируем автоматически, ждём подтверждения кнопкой в чате
  (см. выше).
- Проигранная гонка за бесплатный слот (кто-то забронировал раньше) — `watch_request`
  остаётся `watching`, короткое уведомление в чат опционально, наблюдение продолжается.
- Невалидные/просроченные креды кабинета — `watch_request` → `failed`, обязательный алерт в
  чат с причиной (не молчим).
- `watch_request` без результата к концу `date_to` — автоматически → `expired`, уведомление
  в чат.
- Команда отмены наблюдения в чате (обязательна — иначе логист не может остановить активный
  вотчер).

## Тестирование

- `max_client` / `ozon_client` / `wb_client` — юнит-тесты на замоканных HTTP-ответах
  (`respx`/`httpx`-mock), тот же подход, что `FakeClient` для ClickHouse в существующих
  тестах проекта.
- Оркестрация flows — тесты с фейковыми клиентами: слот сразу, слот появляется через N
  опросов, платный слот → запрос подтверждения (без авто-брони), проигранная гонка,
  невалидные креды.
- Джобы алертов — вызов функции джоба напрямую (без реального таймера APScheduler) с
  фейковой `bot_state.db`; проверка дедупа (`alert_log`) и пороговой логики по времени.
- Реальные вызовы к Ozon/WB/MAX API — вне pytest-набора; отдельный ручной sandbox-скрипт
  для проверки на настоящих ключах (не часть CI).

## Открытые вопросы (проверить на реальных ключах перед/во время реализации)

1. **Ozon**: видит ли API черновик поставки, созданный вручную в личном кабинете (нужно для
   способа B)? Если нет — реализуем fallback с ручным вводом `draft_id`.
2. **Ozon**: точные имена полей ответа `/v2/draft/timeslot/info` (семантика коэффициента) и
   точный эндпоинт подтверждения брони (`/v1/draft/supply/create` — по аналогии, не
   подтверждено официальной документацией напрямую).
3. **Wildberries**: есть ли скрытый (недокументированный) метод бронирования даты поставки,
   которым пользуется личный кабинет — проверить через сетевые запросы браузера в ЛК
   (DevTools). Не блокирует реализацию v1 (WB в любом случае стартует с алертами), но может
   расширить scope позже.
4. **Wildberries**: точный лимит запросов к `acceptance/coefficients` для конкретного
   аккаунта (вторичные источники называют единицы запросов в минуту — подтвердить, чтобы не
   получить блокировку).
5. Пороговые значения по умолчанию (`ALERT_HOURS_BEFORE_DEADLINE`,
   `FBS_POLL_INTERVAL_MINUTES`, дедуп-период WB-алертов) — заданы как разумные умолчания
   выше, уточняются с пользователем при реализации/по факту использования.

## Вне рамок v1

- Точный расчёт суммы штрафа по актуальным формулам Ozon/WB (только пороговый алерт по
  времени).
- Автоматическая бронь FBO-слотов для Wildberries (только алерты; см. «Важные ограничения»).
- Webhook-транспорт для MAX-бота (только long polling; webhook — если появится публичный
  домен с сертификатом).
- Управление доступом на уровне отдельных пользователей внутри рабочего чата (весь чат
  считается доверенным).
